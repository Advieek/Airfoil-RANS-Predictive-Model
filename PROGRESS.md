## 2026-07-11 — found and fixed a real evaluation bug (chunked k-NN); corrected the historical record

The full-scale GraphSAGE eval showed a surprising Cl regression (Spearman 0.826, worse than every other model including its own scarce-task predecessor) alongside a Cd improvement. Investigated rather than accepting it at face value.

**Root cause, confirmed empirically**: `evaluate.py`'s `chunked_predict` splits each test sim's points into 50,000-point chunks (a leftover default from when chunking was purely a memory-management convenience for the MLP). For GraphSAGE, each chunk gets its *own independent* k-NN graph -- points near a chunk boundary lose real spatial neighbors that happen to fall in a different chunk. Test: re-ran full-scale GraphSAGE eval with a chunk size large enough that every sim (max 202,823 points) fits in one chunk, i.e. one true k-NN graph per sim. Result: Cl Spearman 0.826 → **0.976**, Cl rel. error 1.290 → **0.415**, Cd also improved (11.43 → 8.40 rel. error). Confirms the regression was a pure evaluation artifact, not a real model problem.

**Fixed properly, not just patched with a bigger number**: `chunked_predict` now only chunks by point count for the plain MLP (where it's genuinely harmless -- predictions are per-point independent). For any model with `build_graph` (GraphSAGE), it always uses one chunk per simulation, matching how the model would actually be used for a real single-shot prediction.

**Re-ran evaluation on both GraphSAGE checkpoints to correct the historical record** -- this bug affected the *original* scarce-task GraphSAGE eval too, not just the new one:
- Full-scale GraphSAGE (trained at 64k pts/sim): Cl Spearman 0.976, Cl rel. err 0.415, Cd rel. err 8.40, Cd Spearman 0.105. Clean improvement, no surprises.
- **Scarce-task GraphSAGE (trained at only 16k pts/sim), re-evaluated: Cl Spearman 0.804 (not the previously-reported 0.966), Cl rel. err 2.815 (not 0.427).** The originally-reported "good" scarce-GraphSAGE numbers (from the very first Step 9 `morning_after.sh` run) were themselves an artifact of the same bug -- not genuine model quality. Correcting this on the record now.

**Why the *direction* of the fix differed between the two checkpoints** (full-scale improved, scarce got worse) -- this is the actually-interesting finding, not just "bug fixed, numbers changed": GraphSAGE's k-NN graph has a characteristic spatial scale set by whatever point *density* it was trained on (16k pts/sim for the scarce model, 64k for the full-scale model, spread over the same physical domain). Evaluating at full mesh resolution (~180k pts/sim) means neighbors are packed far more tightly than either model saw during training -- a real train/eval density mismatch, separate from the chunking bug. The old chunked-eval's arbitrary 50k index-based chunks happened, by accident of how AirfRANS stores mesh points in spatially-coherent order, to produce local sub-graphs whose density landed closer to the *scarce* model's 16k-point training density (flattering it) while being a worse match for the *full-scale* model's 64k training density (hurting it). Once evaluated honestly (one true graph over all points, no artificial density shift from chunking), the *real* density mismatch is exposed for the scarce model but is much smaller for the full-scale model, because 64k is simply closer to full resolution's ~180k than 16k is.

**Practical conclusion**: training GraphSAGE at higher point density doesn't just improve in-distribution accuracy -- it directly buys better generalization to full-resolution deployment, by narrowing this density mismatch. This is an additional, previously-unrecognized reason the full-scale run was worth doing, on top of the accuracy gains from more data.

Scripts written for this investigation: `scripts/diagnose_graphsage_chunking.py` (isolates the chunking-vs-density-mismatch question), `scripts/reeval_graphsage_scarce_fixed.py` (re-evaluates the scarce checkpoint with the bug fixed and `knn_backend` forced to `cpu_kdtree` explicitly, since that older checkpoint predates the `knn_backend` field in `model_kwargs` and would otherwise default to the much slower `mps_chunked` path). `src/evaluate.py` itself is fixed for all future evaluations. MLP results are completely unaffected by any of this (no graph, no density dependence).

## 2026-07-08, night — true resumable checkpointing added (not just weight warm-start)

User asked why each recovery restarted the epoch counter / LR schedule from scratch, given checkpoints existed and TensorBoard shows full history. Answer: the checkpoint format only ever saved `model_state` (weights) -- not optimizer state (Adam momentum/variance), not the LR scheduler's position, not an epoch counter to resume the loop from. `--init-from` was a *warm start* (good initialization, fresh 400-epoch cosine schedule restarting at epoch 0), not a *true resume*. TensorBoard just renders whatever's in the log directory -- it has no ability to feed state back into a new process; that's purely a function of what `torch.save`/`torch.load` capture.

Given each of these incidents has cost most of a day of wall-clock progress, implemented real resumability in `src/train.py`:
- **`save_resume_checkpoint()`**: saves `model_state` + `optimizer_state` + `scheduler_state` + `epoch` + `best_val` to `checkpoints/<run_name>_resume.pt`, called every `--checkpoint-every` epochs (default 10, per the user's request) and once more at the RSS-limit safety exit (so that exit path is now itself resumable, not just weight-recoverable).
- **`--resume-from <path>`**: loads all of the above and continues the *same* run -- same run directory (TensorBoard event files accumulate in place rather than starting a new colored line), same CSV (opened in append mode, header only written on a fresh run), optimizer/scheduler state restored exactly, loop starts at `epoch+1`. Distinct from `--init-from`, which is kept as-is for genuinely wanting a fresh schedule with pretrained weights (e.g. starting an entirely new experiment).
- Worst-case progress loss after a crash is now bounded by `--checkpoint-every` (≤10 epochs), not however many epochs had accumulated since the last best-val improvement.

## 2026-07-08, morning — MPS memory leak found and fixed in mlp_full_fullres

During a routine 2-hourly check-in (epoch 191/400, val_loss 0.327), a low CPU%(22%) reading on the MLP process prompted a memory check. Found a serious leak:
- `vm_stat`: free pages down to ~83MB (from tens of GB earlier), ~28GB tied up in the memory compressor, heavy cumulative swap activity.
- `top -o mem`: the MLP process (PID 10190) was using **219GB MEM / 139GB compressed** on this 64GB machine.
- **Root cause**: `--full-resolution --sims-per-batch 4` means every training step concatenates 4 *different* simulations at *full, unsubsampled, variable point count* (~150k-220k pts each, no two sims the same size) into one batch. With 800 train sims shuffled every epoch, almost every one of the ~200 steps/epoch has a batch size that has never occurred before. PyTorch's MPS caching allocator retains freed blocks per-shape for reuse, but with shapes this variable, blocks essentially never get reused — the cache grows effectively without bound over a multi-hour run instead of plateauing. GraphSAGE was *not* affected: it uses a fixed `--n-points 64000` (always the same shape every step), so its cache saturates and stays flat.
- **Action taken (in order)**: killed the leaking process (`kill -TERM`, confirmed dead) *before* it could trigger a kernel OOM-kill that might have taken the paused GraphSAGE process down with it. Verified memory fully recovered (~55GB free) immediately after. Verified the best checkpoint was intact and current (`checkpoints/mlp_full_fullres_best.pt`, val_loss 0.277 @ epoch 190) — **zero progress lost**, backed it up to `checkpoints/mlp_full_fullres_epoch190_backup.pt` before touching anything further.
- **Fix**: added periodic `torch.mps.empty_cache()` calls to `src/train.py`'s training/validation loops (every 20 steps, plus once at the end of each phase) — a standard mitigation for MPS/CUDA caching-allocator growth under highly variable tensor shapes.
- **Also added `--init-from <checkpoint>`** (warm-start model weights from a saved checkpoint) so the fix could be verified *and* the 190 epochs of progress preserved in one move, rather than discarding it and starting over.
- **Verified the fix**: 5-epoch smoke run warm-started from the epoch-190 checkpoint. Confirmed warm-start works (epoch 0 val_loss 0.287, matching the loaded checkpoint, not a random-init ~0.70) and memory now fluctuates (16G→37G→23G) instead of climbing monotonically — periodic `empty_cache()` is releasing memory as intended. Smoke run's val_loss improved further to 0.252 by epoch 4. Memory fully clean (~51GB free) after the process exited normally.
